02 / TWO REASONS TO RETURN

养成有两条线：能力，与情感。

同一位从者，既是阵容中的能力组合，也是玩家持续认识的角色。点击节点，查看它如何连接下一次投入。

角色定义

职阶、稀有度、卡组、技能、宝具与特性定义“这是谁”。要区分固定身份与可成长的数值。

战斗接口

从者能力经由编队、礼装与关卡条件进入战斗。阵容价值取决于组合与任务，不宜只用星级解释。

成长培养

等级、再临、技能和宝具等提供不同投入目标。记录每项的前置、资源、上限与收益，避免只罗列养成按钮。

内容与关系

卡面、语音、资料、羁绊与幕间让角色被反复理解。每项内容有自己的开放条件，不能画成统一升级链。

持有与管理

筛选、排序、锁定与保管服务于查找和保护。锁定状态可以与装备状态、成长进度同时存在。

外部连接

获取接召唤与活动，培养接经济，使用接战斗，展示接支援。接口应标注输入与输出，而非只连系统名称。

设计推断

战斗接触可能增加角色熟悉度，角色内容可能增强投入意愿。两条循环互相促进的程度，需要玩家行为与访谈支持；不能把“有养成”直接写成“提升留存”。

03 / THE ECONOMY BENCH

把“资源不够”，拆成可调的变量。

拖动参数，观察时间如何经由体力、关卡与材料转换为成长。这里是教学模型，不是 FGO 真实收益模拟器。

GATE体力入场
SOURCE关卡奖励
CONVERTER强化

假设：无初始库存，无体力溢出与额外恢复；全部体力投入同一关卡；单次产出固定。按 24 小时连续恢复计算，未完成一次入场的余量保留。

资源与机制

体力是资源，恢复是来源，扣除是消耗；不足时阻止入场，则体现门槛作用。一个对象可以承担多种作用。

转换与消耗

强化消耗金币与材料，同时产生成长结果。金币退出库存，并不意味着玩家获得的价值消失。

库存与节奏

期末库存 = 期初库存 + 流入 − 流出。还要问：玩家距离目标多远，哪项资源是当前瓶颈？

交互示意 · 虚构玩家与数值 · 不连接游戏账号
CHALDEA / SIMULATION

需求出现在哪里，互助入口就在哪里

在战前选择支援，玩家已经知道当前关卡需求。战后再提供好友申请，则让“是否建立关系”有一次使用体验作为依据。代价是候选不合适时，刷新与筛选会打断出击节奏。

供给方与借用方是两条循环

借用方追求通关或效率；提供方配置养成成果、获得回报与展示机会。系统要同时关注查找时间、供给更新和持续使用，不能只统计好友数量。

关系状态与支援配置分开记录

申请中、已成为好友描述关系；通常与活动配置描述供给；某次选中的支援描述临时使用。它们并非同一条升级链，关注也应作为独立的单向关系。

从设计推断走向证据

如果认为筛选减少查找成本，就观察找到支援的用时、刷新次数和退出情况；如果认为申请入口促进长期互助，就追踪申请、接受以及后续再次使用。

05 / FROM PLAY TO SPECIFICATION

把体验，写成别人能继续工作的规则。

同一份笔记分成观察、模型、推断和验证四层。展开下面的工作卡，将这套方法迁移到下一个系统。

01记录交互，而非只截界面＋

触发情境 → 操作 → 系统处理 → 可见反馈 → 新状态。每条观察记录操作前后数值、条件与入口。优先覆盖正常路径、容量已满、资源不足和取消等常见情境。

02用五种模型回答五个问题＋

循环解释为什么回来；资源流解释价值如何产生、转换与消耗；状态模型解释对象如何变化；规则表说明条件与结果；依赖图说明系统之间交换什么。模型按问题选择，不为凑齐而绘制。

03状态不是操作按钮的排列＋

“获得 → 锁定 → 强化 → 装备”只是一种操作流程。锁定、装备关系与等级可以同时存在。应分别记录保护状态、所属角色、成长数值，再说明各操作改变哪些字段。

04规则与参数分开写＋

规则：等级上限由稀有度决定。参数：每种稀有度对应的上限。功能说明至少包含入口、条件、输入、消耗、结果、反馈和返回位置；配置只保留实际使用的字段。

05设计判断必须带上代价＋

“这个功能好用”还不够。写成：观察到的机制 → 改变的成本或条件 → 可能引发的行为 → 收益与代价。例如低负担支援便于参与，但不必然形成深度社交。

06验收正确，与验证有效＋

功能验收：申请后显示等待，接受后关系更新，锁定后限制删除。效果验证：玩家是否能更快找到合适支援，是否愿意持续使用。前者由明确规则检查，后者需要真实玩家与行为证据。
